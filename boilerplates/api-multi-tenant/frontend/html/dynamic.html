Enfoque B: ORM raw dinámico (header X-Tenant)

El handler GET /products/dynamic recibe un header X-Tenant: <slug>, lo valida contra la tabla central public.tenants (whitelist), y emite query contra el schema correspondiente con SQL dinámico.

⚠️ Demo, no endpoint compilable: el Enfoque B funciona en fitz run (intérprete) pero hoy NO compila con fitz build debido a 2 deudas residuales del codegen:
  1. Result<List<Map<Str, Any>>> como retorno de handler HTTP no auto-serializa.
  2. r.get("col") sobre DbRow no implementado en codegen (solo intérprete).
El boilerplate solo expone el Enfoque A como binario standalone Dockerizado. Esta página explica el patrón B con código de ejemplo para cuando esas deudas cierren (sub-paso futuro de Fase 10.6 o 5b).

Validación de tenant

Por qué es seguro: el slug se chequea contra public.tenants antes de interpolarlo en el SQL. Tenants no registrados (zeta) → error antes de tocar el schema. SQL injection (' OR 1=1 --) → ni siquiera pasa la validación de la whitelist. Probá los 4 valores del select arriba.

Código del handler

@header(name="X-Tenant")
@get("/products/dynamic")
async fn products_dynamic(x_tenant: Str) -> Result<List<Map<Str, Any>>> {
    let conn = db.connect(db_url).await?

    // PASO CRÍTICO: validar slug contra la tabla central de tenants.
    let tenant_match = Tenant
        .where(fn(t) => t.slug == x_tenant)
        .first(conn)
        .await
    let _ = match tenant_match {
        Ok(_) => null,
        Err(_) => return Err("tenant `{x_tenant}` no existe en `public.tenants`"),
    }

    // Slug whitelisted → safe de interpolar.
    let sql = "SELECT id, name, price, created_at FROM \"{x_tenant}\".\"products\" ORDER BY id"
    return conn.query(sql, []).await
}

Cuándo elegir este enfoque vs Enfoque A

Enfoque A (ORM nativo) Enfoque B (raw dinámico)
Type safety del checker ✅ Sí (compile-time) ❌ Map<Str, Any>
Soporta tenants creados en runtime ❌ Requiere rebuild ✅ Sí (sin rebuild)
Refactor de schema (add column) ✅ Type change + rebuild ⚠️ Cuidado: los responses cambian shape
Performance SQL hard-coded en build SQL construido en runtime
Recomendado para SaaS con ~5-20 tenants fijos SaaS con onboarding self-service de tenants

Los dos enfoques conviven sin conflicto en el mismo backend.
