SaaS Multi-Tenant con Schemas Postgres Custom

Este boilerplate muestra cómo construir un SaaS multi-tenant en Fitz usando schemas Postgres custom (feature de v0.10.21) para aislamiento de datos a nivel DB. Cada cliente vive en su propio schema (acme.products, beta.products, ...) en vez del patrón típico de WHERE tenant_id = X.

¿Por qué schemas custom?

Enfoque Aislamiento Costo migrations Backup por tenant
1 DB / 1 schema / tenant_id column Bajo (bugs en WHERE → leak) Bajo (1 migration para todos) Requiere filtros custom
1 DB / 1 schema por tenant (este boilerplate) Alto (PG schema-level, bug-proof) Medio (1 vez por schema) Trivial (pg_dump --schema=acme)
1 DB por tenant Máximo Alto (cada uno su pool) Trivial
Bug-proof: con schemas custom, es imposible que una query SELECT de tenant_acme accidentalmente lea data de tenant_beta. Postgres bloquea a nivel qualified name ("acme"."products" ≠ "beta"."products"). Sin riesgo de "olvidé el WHERE tenant_id".

Los dos enfoques en este boilerplate

Enfoque A: ORM nativo estático per-tenant

Para SaaS con # de tenants pequeño y fijo (~5-20).

// models.fitz
@table("acme.products") type AcmeProduct {
    @primary id: Int = 0
    name: Str = ""
    price: Float = 0.0
}

@table("beta.products") type BetaProduct {
    @primary id: Int = 0
    name: Str = ""
    price: Float = 0.0
}

// El ORM genera SQL qualified automáticamente:
//   AcmeProduct.all(conn)
//   → SELECT "id","name","price" FROM "acme"."products"

@get("/acme/products")
async fn acme_products() -> Result<List<AcmeProduct>> {
    let conn = db.connect(db_url).await?
    return AcmeProduct.all(conn).await
}

✅ Compile-time safe. Sin queries strings dinámicas.
❌ Cada nuevo tenant requiere code change + rebuild.

Probalo: Tenant Acme · Tenant Beta

Enfoque B: ORM raw dinámico con whitelist

Para SaaS con tenants creados en runtime.

// main.fitz
@header(name="X-Tenant")
@get("/products/dynamic")
async fn products_dynamic(x_tenant: Str) -> Result<List<Map<Str, Any>>> {
    let conn = db.connect(db_url).await?

    // PASO CRÍTICO: validar slug contra whitelist (la tabla
    // central `public.tenants`) ANTES de interpolar. Sin esto,
    // SQL injection seguro. CON esto, imposible — solo los slugs
    // registrados son aceptados.
    let tenant_match = Tenant.where(fn(t) => t.slug == x_tenant)
        .first(conn).await
    let _ = match tenant_match {
        Ok(_) => null,
        Err(_) => return Err("tenant no existe"),
    }

    // Slug whitelisted → safe.
    let sql = "SELECT id, name, price FROM \"{x_tenant}\".\"products\""
    return conn.query(sql, []).await
}

✅ Soporta N tenants sin rebuild.
❌ Sin type safety del checker. Map<Str, Any> en vez de type concreto.

Probalo: Dinámico (X-Tenant)

Setup del schema en boot

En este boilerplate, el schema init corre en boot del backend (main.fitz → init_db()) con CREATE SCHEMA IF NOT EXISTS idempotente.

En producción real, esto se reemplaza por fitz db migrate con migrations versionadas. @table("schema.name") funciona idéntico en ambos casos — el diff de fitz db diff emite CREATE SCHEMA IF NOT EXISTS automático antes del CREATE TABLE. Ver guía DB y ORM sec 26.c.

Stack

  • Backend: Fitz binario standalone (ORM nativo). Sin Python, sin SQLAlchemy, sin Alembic.
  • DB: Postgres 16 (Alpine).
  • Frontend: HTML/CSS/JS vanilla en nginx. Sin build step, sin node_modules.
  • Proxy: nginx routea /api/* al backend Fitz (same-origin, sin CORS).
